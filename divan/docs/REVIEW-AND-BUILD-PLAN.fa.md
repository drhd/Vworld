## بخش ۱ — فیدبک: معماری کجا درست است (و چرا نباید عوضش کنی)

معماری‌ات جدی و بالغ است. این‌ها را **درست** بسته‌ای و پیشنهاد من این است که قفلشان کنی:

| تصمیم | چرا درست است |
|---|---|
| **دیوان = مغز، n8n = دست‌وپا** | تنها تصمیمی که پروژه را از غرق‌شدن نجات می‌دهد. بازسازی n8n یعنی مرگ. |
| **هسته مستقل از کانال** (بات نازک) | فردا تلگرام فیلتر شد، فقط لایه‌ی ورود عوض می‌شود. این بیمه‌ی حیات محصول است. |
| **تأیید انسانی پیش‌فرض** (مصوبه و خروجی ایجنت) | جلوی «آلودگی داده» و بی‌اعتمادی را می‌گیرد. کمیاب و درست. |
| **ModuleGrant = فیچرفلگ = RBAC، همه یک‌جا** | «صد if» را به دو جدول تبدیل می‌کند. UI از روی گرنت ساخته می‌شود = سادگی واقعی. |
| **قاعده‌ی دروازه** (فاز بعد بدون معیار خروج شروع نمی‌شود) | تنها سد در برابر «خزش دامنه». سوپراپ بدون این، قبرستان است. |
| **قیمت بر دقیقه‌ی صوت/اجرای ایجنت، نه per-seat** | مدل درآمد با هزینه‌ی واقعی هم‌راستا. per-seat ارزش شبکه‌ای را می‌کشد. |
| **دو ایجنت اول، نه بیست‌تا** | انضباط درست. اکثر پلتفرم‌ها اینجا می‌میرند. |

**نتیجه:** ستون فقرات معماری را دست نمی‌زنم. کاری که می‌کنم فقط **پرکردن شکاف‌ها** و **تبدیل نقشه به کد** است.

## بخش ۲ — چیزهایی که در سند نیست و باید همین حالا تصمیم بگیریم

اینها ایراد نیستند؛ نقاط کوری‌اند که اگر الان حل نشوند، فاز اپ و ایجنت را قفل می‌کنند. هر کدام یک تصمیم کوچک لازم دارد.

### ۲.۱ 🔴 ذخیره‌ی فایل و مدیا — بزرگ‌ترین شکاف مدل داده
مدل داده‌ات ۱۸ موجودیت دارد ولی **هیچ‌جا نمی‌گوید بایت‌ها کجا می‌روند.** جلسه فایل صوتی دارد، ایجنت محتوا عکس تولید می‌کند، فایلِ `client_visible` برای پرتال کارفرما لازم است. سه گزینه:
- ❌ داخل Postgres (BLOB) — دیتابیس را می‌ترکاند، بکاپ را سنگین می‌کند. غلط.
- ✅ **MVP:** یک volume محلی + یک `StorageAdapter` (interface). فایل روی دیسک، مسیرش در DB.
- ✅ **بعد:** همان interface به S3-compatible (MinIO خودمیزبان / آروان / لیارا) وصل می‌شود — صفر تغییر در کد بالادست.

**تصمیم پیشنهادی:** یک موجودیت `Attachment(id, tenant, owner_type, owner_id, path, mime, size, client_visible)` + یک ماژول `storage.py` با دو تابع `put/get`. از روز اول. این تنها اضافه‌ی مدل داده است که پیشنهاد می‌کنم **قبل** از فاز اپ انجام شود.

### ۲.۲ 🟠 «بات مستقیم به DB» حتی موقتی‌اش هم تله است
سند خودش اعتراف می‌کند بات فعلاً مستقیم به دیتابیس وصل است و «بعداً» از API می‌خواند. تجربه می‌گوید این «بعداً» هیچ‌وقت نمی‌آید و به یک بازنویسی دردناک تبدیل می‌شود.

**راه‌حل بدون هزینه‌ی اضافی:** از همین اول یک لایه‌ی `core/services/` بساز (توابع کسب‌وکار: `create_task`, `approve_decision`, `list_project_tasks`...). بات این توابع را صدا می‌زند، **نه ORM را مستقیم**. وقتی FastAPI آمد، فقط یک پوسته‌ی HTTP نازک روی همان services می‌شود. یعنی:
```
بات  ┐
اپ   ┼──►  core/services/  ──►  DB
API  ┘        (تنها جایی که منطق هست)
```
«پورت‌کردن خدمات بات روی اپ» (خواسته‌ی شماره ۲ تو) دقیقاً به همین دلیل **تقریباً رایگان** می‌شود: هر دو یک services را صدا می‌زنند. این مهم‌ترین بهبود من به معماری توست.

### ۲.۳ 🟠 AgentRun ناهمگام، بدون تایم‌اوت = ران‌های گیرکرده تا ابد
مدل ایجنت callback از n8n می‌گیرد. اگر n8n جواب ندهد (کرش، خطا، شبکه)، آن AgentRun تا ابد در وضعیت `running` می‌ماند. لازم است:
- `correlation_id` روی هر ران (که callback درست را به ران درست وصل کند)
- `timeout_at` + یک reaper در همان حلقه‌ی ریمایندر موجود که ران‌های گیرکرده را `failed` کند
- idempotency: اگر callback دوبار آمد، دوبار تحویل نده

### ۲.۳.۵ 🟡 اطلاع‌رسانی چندکاناله = یک جدول outbox، نه کد per-کانال
خواسته‌ات «API برای push/email/sms» بود. اگر برای هرکدام جدا کد بنویسیم، آشوب می‌شود. الگوی درست: یک جدول `Notification(channel, target, payload, status)` که همه‌چیز در آن ریخته می‌شود و یک worker آن را می‌فرستد. batch و rate-limit تلگرام هم همین‌جا یک‌بار حل می‌شود.

### ۲.۴ 🟡 اینستاگرام «که n8n منتشرش می‌کند» تنها چیزی است که ساده نیست
باقی اتصالات (تلگرام، جیمیل، SMS) واقعاً از n8n ساده‌اند. ولی **انتشار خودکار در اینستاگرام** نیاز دارد به: اکانت Business + اپ فیسبوک + بازبینی اپ توسط متا. این محتمل‌ترین چیزی است که «همین‌جوری کار نمی‌کند». 
**مهار:** ایجنت محتوا پست را کامل بسازد؛ اگر API اینستا آماده نبود، خروجی را برای **پست دستی** تحویل بده (فایل + متن + هشتگ آماده). ارزش روی approvalِ API اینستا گیر نکند.

### ۲.۵ 🔴 چندمستأجری = خطرناک‌ترین کلاس باگ. یک کوئری بدون فیلتر tenant = نشت داده بین سازمان‌ها
این جدی‌ترین ریسک امنیتی یک سوپراپ multi-tenant است. مهار ساختاری:
- همه‌ی کوئری‌ها از یک `scoped_session` با فیلتر tenant پیش‌فرض عبور کنند، نه دستی.
- یک تست که ثابت کند کاربر سازمان A هیچ رکورد سازمان B را نمی‌بیند — **قبل از اولین مشتری**.

## بخش ۳ — 🚧 بلاکر واقعی: کد بات کجاست؟

سند می‌گوید بات v0.3 «نوشته و سینتکس‌تست شده». اما در فایل‌های آپلودشده **فقط اسناد طراحی است، نه کد.** برای اینکه خواسته‌ی شماره ۱ و ۲ تو را (راه‌اندازی + بهینه/دیباگ بات موجود) بدون دوباره‌کاری انجام دهم، یکی از این دو را لازم دارم:

- **الف) کد را داری** → از همان فولدر `outputs` که آدرسش را دادی، کل پوشه‌ی `divan/app/` (یا هرچه هست) را zip کن و آپلود کن. من دیباگ/بهینه/یکپارچه‌اش می‌کنم. (مسیر بدون دوباره‌کاری ✅)
- **ب) کد نداری / ناقص است** → بگو، و من از روی همین spec دقیق (که کامل است) از صفر و تمیز می‌سازمش. (spec آن‌قدر کامل هست که این هم امن است)

**تا وقتی این روشن شود، من پایه‌ای می‌سازم که در هر دو حالت لازم است و با هیچ کدی تداخل ندارد** (زیرساخت + اسناد + قواعد). این سند و فایل‌های کنارش همان پایه‌اند.

## بخش ۴ — تعریف MVP: «دروازه‌ی صفر» دقیقاً یعنی چه

طبق قاعده‌ی دروازه‌ی خودت، MVP وقتی تمام است که این حلقه **روی تلگرام واقعی** کار کند:

```
ویس جلسه → [صف] → رونوشت + خلاصه + صورت‌جلسه + مصوبات پیشنهادی
   → کاربر مصوبه را ✅/❌ می‌کند → تسک با مسئول + مهلت شمسی
   → ریمایندر خودکار → تیک انجام → آرشیو در تاپیک گروه
```
به‌علاوه‌ی: multi-tenant با کد دعوت، پروفایل/موضوع/پروژه، ۴ نقش، پنل مدیریت، جست‌وجو.

**معیار خروج (بدون این‌ها فاز بعد شروع نمی‌شود):**
- [ ] ۷ روز بدون کرش
- [ ] ۱۰ جلسه‌ی واقعی پردازش‌شده
- [ ] تیم صورت‌جلسه‌ی دستی را کنار گذاشته
- [ ] بکاپ pg_dump آزموده‌شده (یک‌بار واقعاً restore شده)
- [ ] کیفیت تفکیک گوینده‌ی فارسی روی صوت واقعی مکتوب شده

**هر چیز دیگری (API, Mini App, ماژول, ایجنت, پرتال) بعد از این دروازه است. نقطه.**

## بخش ۶ — قواعد مهندسی که همین‌جا قفل می‌کنیم

اینها همان «ماشینی که بی‌وقفه تعمیر می‌شود» است، عملیاتی‌شده:

1. **جداسازی پروسه:** هر سرویس کانتینر جدا (bot/worker/db/redis/n8n). کرش یکی، بقیه زنده.
2. **Alembic از جدول اول.** هر تغییر اسکیما = یک مهاجرت versioned و قابل rollback.
3. **هیچ منطقی در handler نیست** — handler فقط ورودی می‌گیرد و `core/services` را صدا می‌زند. (قابل تست، قابل استفاده مجدد در API)
4. **هیچ رابطی مستقیم به ORM دست نمی‌زند** — فقط از طریق services.
5. **ورژن‌بندی معنایی + CHANGELOG فارسی.** هر نسخه یک تگ گیت.
6. **secretها فقط در env، هرگز در گیت.** `.env` در `.gitignore`. فقط `.env.example` commit می‌شود.
7. **Feature flag = ModuleGrant.** قابلیت خاموش دیپلوی می‌شود، برای یک نفر روشن، تست، بعد همه.
8. **تأیید انسانی پیش‌فرض** برای هر خروجی که به بیرون می‌رود (مصوبه، پست ایجنت، تحویل کارفرما).
9. **همه‌ی کوئری‌ها tenant-scoped.** بدون استثنا.

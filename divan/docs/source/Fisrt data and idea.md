# دیوان — طراحی محصول و اپلیکیشن
**نسخه ۱.۰ | مخاطب: تیم فنی و تصمیم‌گیر محصول**

---

## ۱. تز مرکزی

بیشتر ابزارهای مدیریت پروژه یک **دفترچه‌ی خالی** به آدم می‌دهند و منتظر می‌مانند که پرش کند. مشکل این است که پرکردن دفترچه خودش کار است — و اولین کاری است که زیر فشار حذف می‌شود. برای همین ۹۰٪ فضاهای کاری Notion و Asana بعد از سه هفته می‌میرند.

دیوان از جای دیگری شروع می‌کند: **صدا**.

آدم‌ها به‌هرحال جلسه می‌گذارند و حرف می‌زنند. آن صحبت، ماده‌ی خامی است که همین حالا تولید می‌شود و کسی برای تولیدش تلاش اضافه نمی‌کند. دیوان همان را می‌گیرد و به ساختار تبدیل می‌کند: صورت‌جلسه، مصوبه، تسک، مسئول، مهلت.

> **دفترچه پر می‌شود، بدون آنکه کسی پرش کند.**

این تنها تمایز واقعی محصول است. هر چیز دیگری — پروژه، لایه، گزارش، CRM — لایه‌ای است که روی این هسته می‌نشیند. اگر این هسته کار نکند، بقیه بی‌معنی است.

## ۲. سه لایه‌ی محصول

```
┌─────────────────────────────────────────────────┐
│  لایه‌ی ورود (Interface)                        │
│  تلگرام · بله · وب · موبایل · هر پیام‌رسان دیگر  │
│  ← نازک، قابل تعویض، هیچ منطقی ندارد            │
├─────────────────────────────────────────────────┤
│  لایه‌ی هسته (Core)                             │
│  موجودیت‌ها · قواعد · گردش کار · دسترسی         │
│  ← تمام ارزش اینجاست. مستقل از پیام‌رسان.       │
├─────────────────────────────────────────────────┤
│  لایه‌ی هوش (Intelligence)                      │
│  صوت→متن · تفکیک گوینده · استخراج مصوبه · خلاصه │
│  ← adapter، provider قابل تعویض                 │
└─────────────────────────────────────────────────┘
```

**قاعده‌ی حاکم:** هیچ منطق کسب‌وکاری در لایه‌ی ورود نوشته نمی‌شود. اگر فردا تلگرام فیلتر شد یا بله جایگزین شد، فقط لایه‌ی بالا عوض می‌شود و صفر خط از هسته دست نمی‌خورد.

این تصمیم امروز هزینه دارد (کد بیشتر) و فردا نجات‌دهنده است.

## ۳. استراتژی چندکاناله

### چرا بله جدی است
بله رسماً اعلام کرده API بازوهایش با تلگرام سازگار است و ربات‌های تلگرامی مستقیم منتقل می‌شوند. آدرس پایه‌اش `tapi.bale.ai/bot<token>/` است — یعنی همان کد aiogram با تغییر یک متغیر کار می‌کند. بله محصول بانک ملی ایران است و از داخل ایران بدون فیلتر باز است.

**یعنی: دومین کانال، تقریباً رایگان.**

### تفاوت استراتژیک دو کانال

| | تلگرام | بله |
|---|---|---|
| دسترسی از ایران | فیلتر — نیاز به VPN | باز |
| سرور میزبان | باید خارج باشد | سرور ایرانی هم می‌شود |
| مخاطب | عمومی، تیم‌های تکنیکال | سازمانی، بانکی، دولتی |
| بلوغ API | کامل | سازگار ولی ناقص‌تر |
| درگاه پرداخت | ندارد (Stars) | دارد — ریالی |

**نکته‌ای که اغلب دیده نمی‌شود:** درگاه پرداخت ریالی بله یعنی می‌توانی اشتراک دیوان را **داخل خود بله** بفروشی، بدون سایت و درگاه جدا. برای محصول ایرانی این یک مزیت جدی است، نه یک جزئیات فنی.

### الگوی استقرار پیشنهادی
```
        سرور خارج                    سرور ایران
       ┌──────────┐                 ┌──────────┐
       │ bot      │                 │ bot_bale │
       │ telegram │                 │          │
       └────┬─────┘                 └────┬─────┘
            └──────────┬─────────────────┘
                  ┌────▼────┐
                  │ هسته +  │
                  │ دیتابیس │
                  └─────────┘
```
یک محصول، یک دیتابیس، دو در ورودی. کاربر از هرکدام وارد شود همان داده را می‌بیند.

### کانال‌های بعدی
هر پیام‌رسانی که Bot API سازگار با تلگرام داشته باشد تقریباً رایگان اضافه می‌شود. برای بقیه (واتساپ، دیسکورد، ایتا، روبیکا) یک adapter لازم است — ساختار `app/channels.py` برای همین آماده شده. **اما این کار فاز ۳ است، نه حالا.**

## ۴. مدل مدیریت پروژه — چرا دو محور

اکثر ابزارها پروژه را یک **لیست تسک** می‌بینند. مشکل: لیست فقط می‌گوید چه کارهایی مانده، نمی‌گوید پروژه **کجاست** و **کدام جنس کار عقب است**.

دیوان دو محور مستقل دارد:

**محور اول — فاز (زمان):** پروژه در چه مرحله‌ای است. ترتیبی است. هر فاز یک **معیار خروج (gate)** دارد.
```
🟢 تعریف ← 🔵 طراحی ← ⚪️ اجرا ← ⚪️ تثبیت
```

**محور دوم — لایه (جنس کار):** موازی است، نه ترتیبی. استراتژی، اجرا، برند، مالی — همه هم‌زمان جلو می‌روند.

**تقاطع = ماتریس:**
```
لایه\فاز      1    2    3    4
🧠استراتژی    ·    2    ·    ·
⚙️اجرا        ·    1    5    ·
🎨برند        ·    ·    3    ·
💰مالی        4    ·    ·    ·
```

این جدول در یک نگاه چیزی می‌گوید که لیست تسک هرگز نمی‌گوید: **لایه‌ی مالی در فاز اول گیر کرده در حالی که بقیه رفته‌اند فاز سوم.** این یعنی یک ریسک ساختاری، نه یک تسک عقب‌افتاده.

**قاعده‌ی طراحی:** هر تسک باید بداند در کدام فاز و کدام لایه است. بدون این دو، تسک فقط یک یادداشت است.

## ۵. اپلیکیشن — چه چیزی به بات اضافه می‌کند

بات برای **ثبت و اقدام** عالی است: ویس بفرست، دکمه بزن، تیک بزن. برای **دیدن** ضعیف است — تلگرام جدول درست نشان نمی‌دهد، نمودار ندارد، و مقایسه‌ی چند پروژه در آن غیرممکن است.

### تقسیم کار پیشنهادی

| کار | بات | اپ |
|---|---|---|
| فرستادن ویس جلسه | ✅ طبیعی | — |
| تیک‌زدن تسک و چک‌لیست | ✅ سریع‌تر | ✅ |
| نوتیف و ریمایندر | ✅ فقط اینجا | — |
| دیدن ماتریس پروژه | محدود | ✅ اصلی |
| تایم‌لاین و گانت | ❌ | ✅ |
| خواندن رونوشت بلند | ضعیف | ✅ |
| گزارش تحلیلی و نمودار | ❌ | ✅ |
| تنظیمات و دسترسی‌ها | محدود | ✅ |
| جست‌وجوی پیشرفته | محدود | ✅ |

**قاعده:** اپ جایگزین بات نیست، **مکمل بینایی** آن است. کاربر ۸۰٪ وقت در بات است و برای «دیدن کل تصویر» به اپ می‌رود.

### مسیر ساخت اپ — سه گام

**گام ۱ — Mini App داخل خود پیام‌رسان (توصیه‌ی اول)**
تلگرام و بله هر دو Mini App دارند. یک صفحه‌ی وب که داخل پیام‌رسان باز می‌شود.
- نصب نمی‌خواهد، فروشگاه اپ نمی‌خواهد، احراز هویت مجانی است (کاربر از قبل لاگین است)
- **بهترین نسبت ارزش به هزینه**

**گام ۲ — وب اپ مستقل**
همان کد Mini App با یک لایه‌ی لاگین، روی دامنه‌ی خودت. برای مدیرانی که با لپ‌تاپ کار می‌کنند و برای فروش سازمانی («ما وب پنل داریم») لازم است.

**گام ۳ — اپ موبایل نیتیو**
فقط اگر قابلیتی لازم شد که وب نمی‌دهد (ضبط پس‌زمینه، آفلاین کامل، ویجت). **احتمالاً هرگز لازم نمی‌شود.** این گام را تا وقتی مشتری صریحاً نخواسته شروع نکن.

### صفحه‌های اپ (اولویت‌دار)
1. **داشبورد** — تسک‌های امروز، جلسات پیش رو، پروژه‌های در خطر
2. **پروژه** — ماتریس فاز×لایه، تایم‌لاین، کامنت‌ها
3. **جلسه** — رونوشت با قابلیت پرش به گوینده، صورت‌جلسه، مصوبات
4. **پروفایل/موضوع** — همه‌چیزِ یک شخص در یک صفحه
5. **گزارش** — نرخ انجام، روند، مقایسه‌ی لایه‌ها
6. **مدیریت** — اعضا، دسترسی، اتصال‌ها، مصرف

**اصل طراحی بصری:** چگالی بالا، حرکت کم. این ابزار کار است نه شبکه‌ی اجتماعی. راست‌چین کامل، تاریخ دوگانه در همه‌جا، تایپوگرافی فارسی درست (Vazirmatn).

## ۶. اتصال به بیرون (CRM و بقیه)

«اتصال به هر سیستمی» اگر مستقیم پیاده شود یعنی N کانکتور دست‌ساز و بدهی فنی ابدی. معماری درست سه لایه دارد:

**۱. لایه‌ی خروج داده (آماده است)** — هر پروفایل/موضوع/پروژه یک ZIP با `raw_data.json` ساختاریافته می‌دهد. همین حالا هر سیستمی می‌تواند آن را بخورد.

**۲. لایه‌ی رویداد (فاز بعد)** — Webhook خروجی روی رویدادها: `meeting.processed`، `task.done`، `phase.completed`.

**۳. لایه‌ی نگاشت (فاز بعد)** — جدول `CRMMapping` که می‌گوید فیلد X ما با فیلد Y آن‌ها متناظر است.

**تصمیم کلیدی:** به‌جای نوشتن کانکتور برای هر CRM، یک نمونه‌ی **n8n خودمیزبان** به‌عنوان میان‌افزار. هر اتصال جدید = یک workflow، نه کد جدید در دیوان. این «اتصال به همه‌چیز» را با هزینه‌ی نگهداری نزدیک صفر می‌دهد.

**زمان‌بندی:** تا وقتی نمی‌دانیم مشتری به کدام CRM وصل می‌شود، ساختن کانکتور حدس‌زدن است. فاز ۳.

## ۷. نقشه‌ی راه

| فاز | محتوا | معیار خروج |
|---|---|---|
| **۰ ✅** | اسکلت، پروفایل، موضوع، RBAC، دیپلوی | بات ۷ روز بدون کرش |
| **۱ ✅** | حلقه‌ی صوت→مصوبه→تسک→ریمایندر→آرشیو | ۱۰ جلسه‌ی واقعی، تیم به روش دستی برنگردد |
| **۲ ✅** | پروژه‌ی لایه‌ای، کامنت، خروجی ZIP، بکاپ، بله | یک پروژه‌ی واقعی کامل در دیوان مدیریت شود |
| **۳** | قرار و ریمایندر جلسه، چک‌لیست تکرارشونده، گزارش دوره‌ای، تگ‌گراف | تیم گزارش هفتگی را از دیوان بخواند نه دستی |
| **۴** | Mini App، جست‌وجوی FTS، Alembic | مدیر برای «دیدن» به اپ برود |
| **۵** | Webhook، n8n، جست‌وجوی معنایی، چندسازمانی کامل | اولین مشتری بیرونی |

**قاعده‌ی دروازه:** هیچ فازی قبل از پاس‌شدن معیار خروج فاز قبل شروع نمی‌شود. این تنها محافظ در برابر خزش دامنه است.

## ۸. مدل کسب‌وکار — نکات ساختاری

**جنس محصول:** ابزار تیمی با داده‌ی انباشتی. هرچه تیم بیشتر استفاده کند، هزینه‌ی ترک بیشتر می‌شود — چون تاریخچه‌ی جلسات و مصوبات جای دیگری نیست. این بهترین نوع چسبندگی است و از روز اول باید حفظش کرد: **خروجی گرفتن باید آسان باشد** (اعتماد می‌سازد) ولی تاریخچه ارزش انباشتی دارد.

**واحد قیمت‌گذاری:** دقیقه‌ی صوت پردازش‌شده، نه تعداد کاربر. دلیل: هزینه‌ی واقعی تو دقیقه‌ی صوت است. قیمت‌گذاری per-seat باعث می‌شود تیم‌ها کاربر کم بگیرند و ارزش شبکه‌ای محصول بمیرد. زیرساخت `Usage` از حالا همین را می‌شمارد.

**سه چیزی که قبل از اولین فروش باید حل شود:**
1. **مهاجرت از لایه‌ی رایگان AI** — بند محرمانگی، غیرقابل مذاکره
2. **بکاپ و بازیابی آزموده‌شده** — نه فقط گرفتن بکاپ، بلکه یک‌بار واقعاً restore کردن
3. **قرارداد پردازش داده** — مشتری سازمانی می‌پرسد صوتش کجا می‌رود

## ۹. ریسک‌های محصول

| ریسک | چرا جدی است | مهار |
|---|---|---|
| **کیفیت صوت جلسات واقعی** | همهمه، تداخل، فارسی محاوره‌ی پرانگلیسی — دقت تفکیک گوینده افت جدی می‌کند | راهنمای یک‌صفحه‌ای ضبط؛ ویرایش انسانی سبک؛ انتظار درست به‌جای وعده‌ی بزرگ |
| **اعتماد به مصوبه‌ی خودکار** | یک مصوبه‌ی اشتباه = تصمیم اشتباه = بی‌اعتمادی دائمی | تأیید انسانی اجباری قبل از تبدیل به تسک — همین حالا پیاده است |
| **محرمانگی** | یک نشت = مرگ محصول در بازار سازمانی | مهاجرت به لایه‌ی پولی قبل از اولین مشتری |
| **خزش دامنه** | دقیقاً همان دامی که همه‌ی پلتفرم‌های جاه‌طلب در آن می‌افتند | دروازه‌ی معیار خروج فاز |
| **وابستگی به تلگرام** | فیلترینگ و تغییر سیاست خارج از کنترل ماست | چندکاناله بودن از روز اول — بله همین حالا آماده است |
| **تک‌نفره بودن نگهداری** | اگر یک نفر برود، محصول می‌ایستد | مالکیت ریپو نزد کارفرما، مستندسازی، CI |

# دیوان (Divan) — سند تحویل به تیم فنی
**نسخه: v0.2 (MVP اولیه) | تاریخ: ۱۴۰۵/۰۴/۲۶ — 2026-07-17**
**مخاطب: تیم فنی (تست، دیپلوی، توسعه) | وضعیت: آماده‌ی تست، اجرانشده در محیط واقعی**

> **دیوان:** نهاد ثبت و اداره‌ی امور در ایران باستان — جایی که تصمیم، مصوبه و حساب‌وکتاب ثبت می‌شد.

---

## ۰. این سند چیست و چه انتظاری از تیم است

این یک محصول تمام‌شده نیست. یک **MVP کدنویسی‌شده و سینتکس‌تست‌شده اما در محیط واقعی تلگرام اجرانشده** است. وظیفه‌ی تیم در گام اول **ساختن فیچر جدید نیست**؛ دیپلوی، تست میدانی، و گزارش باگ است. توسعه‌ی فاز بعد فقط پس از عبور از معیار خروج (بخش ۹) شروع می‌شود.

**قاعده‌ی حاکم بر این پروژه:** معماری کامل قفل است، اما ساخت مرحله‌ای است. هر درخواست فیچر جدید خارج از فاز جاری رد می‌شود مگر معیار خروج فاز جاری پاس شده باشد.

---

## ۱. محصول در یک نگاه

دیوان یک بات تلگرامی است که خط تولید «صوت جلسه ← تصمیم اجراشده» را می‌بندد:

```
ویس/فایل صوتی جلسه
   ↓ (بات می‌پرسد: مال کدام پروفایل/موضوع؟ — دکمه‌ای)
   ↓ (صف پردازش — بات آزاد می‌ماند)
هوش مصنوعی: رونوشت تفکیک‌گوینده + خلاصه + صورت‌جلسه + مصوبات
   ↓ (کاربر مصوبات را با دکمه ✅/❌ تأیید یا رد می‌کند)
تسک با مسئول + مهلت شمسی
   ↓
ریمایندر خودکار (۳ ساعت قبل از مهلت) → مسئول نوتیف می‌گیرد
   ↓ (دکمه: ✅ انجام شد / 🔄 در جریان / ⛔ مانع دارم + دلیل → مدیر مطلع می‌شود)
آرشیو خودکار + پین در تاپیک اختصاصی گروه
```

**قابلیت‌های موجود در v0.2:**
- خط کامل بالا
- multi-tenant با کد دعوت (اولین `/start` = سوپر ادمین)
- پروفایل (شخص/طرف کاری) و موضوع (پروژه) با CRUD دکمه‌ای
- چهار نقش: `super_admin` / `manager` / `member` / `guest`
- پنل مدیریت: اعضا، چرخش نقش، کد دعوت، مصرف، لاگ فعالیت
- جست‌وجو در عنوان/رونوشت/خلاصه/صورت‌جلسه/تسک
- یادآور دلخواه با تاریخ شمسی
- تاریخ دوگانه شمسی/میلادی در همه‌ی نمایش‌ها
- AuditLog روی همه‌ی اعمال
- سقف مصرف پردازش صوت (cap داخلی)
- زنجیره‌ی fallback هوش مصنوعی: Gemini → Groq

## ۲. معماری — چرا این‌طوری (این بخش قابل مذاکره نیست)

### مدل مفهومی
اشتباه رایج بات‌های مدیریت جلسه: مدل داده را حول «پیام تلگرام» می‌سازند. در دیوان مدل حول **موجودیت‌های کسب‌وکار** ساخته شده و تلگرام فقط یک **لایه‌ی رابط** است. دلیل: فردا همین هسته می‌تواند رابط وب یا موبایل بگیرد بدون بازنویسی.

```
Tenant (سازمان — کد دعوت جدا، آماده‌ی فروش چندسازمانی)
 ├── User ── Role
 ├── Profile (شخص/طرف کاری)
 ├── Topic (موضوع/پروژه)
 ├── Meeting ── Transcript / Summary / Minutes / Speakers
 ├── Task (منشأ: مصوبه‌ی جلسه یا دستی)
 ├── Reminder
 ├── Binding (نگاشت Profile/Topic → تاپیک تلگرامی)
 ├── Audit
 └── Usage (کنترل سقف مصرف)
```

### سه قاعده‌ی ساختاری
1. **Meeting همیشه به Profile یا Topic متصل است.** جلسه‌ی بی‌صاحب وجود ندارد. دسته‌بندی محصول جانبیِ این اجبار است، نه یک فیچر جدا.
2. **Task فقط با تأیید انسانی ساخته می‌شود.** LLM پیشنهاد می‌دهد، انسان دکمه می‌زند. تسک خودکارِ بی‌تأیید = آلودگی داده.
3. **پردازش سنگین هرگز داخل پروسه‌ی بات اجرا نمی‌شود.** worker جدا (arq). کرش پردازش، بات را نمی‌کُشد. این قاعده‌ی ضدکرش است.

### چرا «تاپیک» و نه «کانال جدا برای هر پروفایل»
کانال جدا per پروفایل scale نمی‌شود (مدیریت ۵۰ کانال = جهنم ادمین). الگوی درست: یک **سوپرگروه Forum** با تاپیک اختصاصی برای هر Profile/Topic فعال. جست‌وجوی بومی تلگرام هم داخل تاپیک کار می‌کند و مکمل سرچ دیتابیسی می‌شود.

### استک
| لایه | انتخاب | دلیل |
|---|---|---|
| بات | Python 3.12 + aiogram 3.x | async-first، FSM، middleware، بالغ‌ترین اکوسیستم |
| DB | PostgreSQL 16 + SQLAlchemy 2 | JSONB، pg_trgm برای FTS فارسی، pgvector در فاز بعد |
| صف/کش/FSM | Redis + arq | قاعده‌ی ضدکرش |
| AI | Adapter زنجیره‌ای (Gemini → Groq) | provider-agnostic؛ payment isolation |
| تقویم | jdatetime — ذخیره UTC، نمایش دوگانه | |
| اتصال | Polling | نه دامنه، نه SSL — روی لپ‌تاپ بالا می‌آید؛ همین Docker بدون تغییر روی VPS می‌رود |
| دیپلوی | Docker Compose (bot / worker / db / redis / botapi اختیاری) | هر جزء جدا کرش کند، بقیه زنده می‌مانند |

## ۳. راه‌اندازی — گام‌به‌گام

### پیش‌نیاز
1. **Docker Desktop** نصب و بالا آمده
2. **VPN سراسری روشن** یا `PROXY_URL` در `.env` — تلگرام و گوگل و Groq هر سه از IP ایران بسته‌اند
3. دو کلید (بخش ۴)

### اجرا
```bash
cp .env.example .env      # کلیدها را داخلش بگذار
docker compose up -d --build
docker compose logs -f bot   # باید ببینی: «📜 دیوان بالا آمد — polling»
```

### اولین ورود
اولین کسی که `/start` بزند → workspace می‌سازد و **سوپر ادمین** می‌شود. کد دعوت در پنل ⚙️ مدیریت نمایش داده می‌شود. بقیه با همان کد عضو می‌شوند.

### تنظیمات BotFather (یک‌بار)
- `/setname`, `/setdescription`, `/setabouttext` → هویت «دیوان»
- `/setprivacy` → **Disable** (فقط اگر می‌خواهی بات در گروه ویس ببیند)

### راه‌اندازی آرشیو
1. یک سوپرگروه با **Topics** بساز
2. بات را **ادمین** کن (بدون ادمین، ارسال در تاپیک و پین کار نمی‌کند)
3. داخل تاپیکِ مربوطه بزن: `/bind p12` (پروفایل ۱۲) یا `/bind t5` (موضوع ۵)
4. از این به بعد خروجی‌های آن پروفایل همان‌جا آرشیو و پین می‌شود

## ۴. کلیدها و APIها

### توکن بات
@BotFather → `/newbot` → نام و یوزرنیم (باید به `bot` ختم شود) → توکنی مثل `7123456:AAH...` → در `.env` جلوی `BOT_TOKEN=`

### کلید Gemini (اصلی)
`aistudio.google.com/apikey` → ورود با اکانت گوگل → «Create API key» → کارت بانکی نمی‌خواهد → `GEMINI_API_KEY=`
⚠️ صفحه از IP ایران باز نمی‌شود.

### کلید Groq (fallback — اختیاری ولی توصیه‌شده)
`console.groq.com/keys` → کلید رایگان → `GROQ_API_KEY=`
زنجیره خودکار است؛ اگر Gemini شکست بخورد (سهمیه/قطعی) بات بی‌سروصدا به Groq می‌رود و در پیام نهایی به کاربر می‌گوید کدام provider جواب داده.

### تفاوت providerها
| | Gemini | Groq (Whisper) | Self-hosted faster-whisper |
|---|---|---|---|
| هزینه | رایگان با سقف | رایگان با سقف سخاوتمندتر | صفر همیشگی |
| تفکیک گوینده | ✅ در همان فراخوان | ❌ فقط متن خام | ❌ نیاز به pyannote جدا |
| خلاصه/مصوبه | ✅ همان فراخوان | فراخوان دوم (LLM متن) | نیاز به LLM جدا |
| نیاز به VPN | بله | بله | فقط یک‌بار برای دانلود مدل |
| سرعت | متوسط | بسیار سریع (LPU) | کند روی CPU، سریع روی GPU |
| دقت فارسی | خوب | خوب (همان Whisper) | همان |

**محدودیت Groq:** دیاریزیشن ندارد. خروجی یک بلوک متن خام است، نه Speaker 1/2. کد این را تشخیص می‌دهد و دکمه‌ی «نام‌گذاری گوینده» را خودکار مخفی می‌کند. برای صورت‌جلسه کافی است؛ برای «چه کسی چه گفت» نه.

**اگر اصلاً به هیچ API خارجی نمی‌رسید:** مشکل VPN/تحریم است نه انتخاب provider — Groq هم آمریکایی است. تنها راه واقعی: Whisper خودمیزبان (بخش ۱۰).

## ۵. ریاضی سقف مصرف — واقع‌بینی

منابع اعداد متناقضی می‌دهند (بعد از تعدیل‌های دسامبر ۲۰۲۵): برای Gemini Flash بین ۱۰ تا ۱۵ درخواست در دقیقه و ۲۵۰ تا ۱۵۰۰ درخواست در روز گزارش شده. خودِ گوگل تصریح می‌کند سقف به منطقه‌ی جغرافیایی و وضعیت تأیید حساب بستگی دارد. **عدد دقیق را از صفحه‌ی رسمی rate limits بگیرید، نه از این سند.**

**اما سقف درخواست گلوگاه ما نیست:** هر جلسه = یک درخواست. ۲۵۰ در روز یعنی ۲۵۰ جلسه در روز.

**گلوگاه واقعی توکن است:** صوت ≈ ۳۲ توکن بر ثانیه. جلسه‌ی ۶۰ دقیقه‌ای ≈ ۱۱۵ هزار توکن. با سقف ۲۵۰ هزار توکن در دقیقه، **جلسه‌ی بالای ~۱۰۰ دقیقه ممکن است رد شود**.
→ راه‌حل فعلی: صوت خیلی طولانی را دو تکه بفرست (هر تکه جلسه‌ی جدا می‌شود).

**سقف حجم فایل:**
- API استاندارد تلگرام: دانلود ۲۰MB — کد این را چک می‌کند و پیام راهنما می‌دهد
- برای فایل بزرگ‌تر: `TELEGRAM_API_ID` و `TELEGRAM_API_HASH` از my.telegram.org + `LOCAL_BOT_API=http://botapi:8081` + `docker compose --profile bigfiles up -d` → سقف به 2GB می‌رود
- سقف حجم فایل Groq در لایه‌ی رایگان از Gemini پایین‌تر است — جلسه‌ی خیلی طولانی ممکن است فقط روی Gemini پردازش شود

**cap داخلی:** `STT_TOTAL_MINUTES=3000` (۵۰ ساعت) — این سقف خودمان است، نه محدودیت گوگل. در پنل مدیریت دیده می‌شود.

## ۶. 🔴 پرچم‌های قرمز — قبل از هر تصمیمی بخوانید

### ۶.۱ محرمانگی (مهم‌ترین بند این سند)
شرایط لایه‌ی رایگان گوگل اجازه می‌دهد پرامپت‌های ارسالی برای آموزش مدل استفاده شود (لایه‌ی پولی و Vertex AI این‌طور نیستند).

**یعنی:** صوت جلسه‌ی قرارداد، مذاکره‌ی مشتری، و هر داده‌ی محرمانه‌ای می‌رود در خط لوله‌ی آموزشی گوگل.
- برای تست داخلی: قابل قبول
- برای **جلسات محرمانه‌ی مشتری** و برای **فروش محصول**: قطعاً نه

**اقدام لازم روز اولِ فروش:** مهاجرت به لایه‌ی پولی (حدود ۰.۳ دلار به ازای هر میلیون توکن ورودی برای Flash) یا provider دیگر. `app/ai.py` به‌صورت adapter نوشته شده دقیقاً برای همین — مهاجرت یعنی افزودن یک تابع، نه بازنویسی.

**در تست میدانی: از جلسات واقعاً محرمانه استفاده نکنید.**

### ۶.۲ کد در محیط واقعی اجرا نشده
COMPILE_OK / IMPORTS_OK / DB_OK پاس شده، اما هیچ‌وقت به سرور واقعی تلگرام وصل نشده. **انتظار ۲–۳ باگ ریز در اولین اجرا معقول است.** این عیب نیست، وضعیت است. لاگ خطا را کامل جمع کنید.

### ۶.۳ استفاده‌ی تجاری از لایه‌ی رایگان
در اروپا/بریتانیا/سوئیس مجاز نیست. برای بازار داخلی موضوعیت ندارد؛ اگر مشتری خارجی آمد مهم می‌شود.

### ۶.۴ برند
مالکیت دامنه و هم‌آوایی نهادی «دیوان» (دیوان محاسبات / دیوان عدالت اداری) قبل از قفل نهایی نام برای محصول فروشی باید چک شود. برای ابزار داخلی مسئله نیست.

## ۷. آنچه در v0.2 **نیست** — شکاف‌های شناخته‌شده

این فهرست صادقانه است. اگر کسی گفت «کامل است»، غلط گفته.

### شکاف‌های فیچری (در مشخصات اولیه بود، هنوز ساخته نشده)
1. **جلسه‌ی آینده / قرار:** الان فقط صوتِ جلسه‌ی برگزارشده پردازش می‌شود. «قرار با تاریخ و ساعت + نوتیف قرارت نزدیک است» وجود ندارد — موجودیت Appointment در مدل داده نیست. **این شکاف اصلی است.**
2. **چک‌لیست / روتین تکرارشونده:** تخصیص چک‌لیست به فرد/گروه، تیک دکمه‌ای، دلیل برای آیتم ردشده، تکرار روزانه/هفتگی — نیست. فقط تسک تکی داریم.
3. **گزارش دوره‌ای:** گزارش روزانه‌ی شخصی و هفتگی مدیر (نرخ انجام تسک، جلسات، مصوبات) — نیست. فقط پنل لحظه‌ای هست.
4. **تگ‌گراف:** ربط‌دادن پروفایل‌ها و موضوعات با تگ مشترک — نیست.

### شکاف‌های زیرساختی
5. **بکاپ دیتابیس ندارد.** با نیت فروش، از دست رفتن داده‌ی مشتری = مرگ محصول. اسکریپت pg_dump شبانه لازم است. **اولویت بالا.**
6. **جست‌وجو ILIKE ساده است**، نه FTS واقعی. روی حجم بالا کند می‌شود.
7. **Alembic راه‌اندازی نشده** — فعلاً `create_all`. برای اولین مهاجرت اسکیما لازم می‌شود.

### آنچه عمداً نیست و **نباید باشد** (فاز ۳)
CRM/n8n، Mini App ادمین‌پنل، جست‌وجوی معنایی (pgvector)، Rich Message tables.
**دلیل:** قبل از PMF داخلی، ساختن این‌ها بدهی فنی است نه ارزش. تناقض «پلتفرم کامل قبل از اعتبارسنجی حلقه‌ی ارزش» باید فعالانه دفع شود.

1. دیپلوی طبق بخش ۳ روی یک ماشین (لپ‌تاپ یا VPS فرقی نمی‌کند)

### 🟡 بعد از تست (v0.3 — فقط پس از عبور از معیار خروج)
1. موجودیت Appointment + ریمایندر قرار (قابل تنظیم: ۱ روز / ۳ ساعت / ۳۰ دقیقه قبل)

3. گزارش دوره‌ای (روزانه‌ی شخصی + هفتگی مدیر)
4. تگ‌گراف

### 🔵 آینده (v0.4+ — فقط پس از مشتری واقعی)

2. Whisper خودمیزبان (اگر پایداری اتصال مسئله شد)
3. Mini App ادمین‌پنل
4. Webhook/n8n برای CRM
5. جست‌وجوی معنایی pgvector

**قاعده:** هیچ آیتم زردی قبل از پاس‌شدن معیار خروج بخش ۹ شروع نمی‌شود.

## ۹. معیار خروج فاز جاری (PMF داخلی)

فاز جاری وقتی تمام است که:
- [ ] بات ۷ روز متوالی بدون کرش زنده بماند
- [ ] حداقل ۱۰ جلسه‌ی واقعی پردازش شده باشد
- [ ] تیم صورت‌جلسه‌ی دستی را کنار گذاشته باشد
- [ ] حداقل ۳ کاربر واقعی از دو نقش مختلف فعال باشند
- [ ] کیفیت تفکیک گوینده‌ی فارسی روی صوت واقعی سنجیده و مکتوب شده باشد

**مهم‌ترین معیار:** اگر تیم خودمان به روش قبلی برنگردد، محصول کار می‌کند. اگر برگردد، افزودن فیچر نجاتش نمی‌دهد — باید علت را پیدا کرد.

| ریسک | مهار |
|---|---|
| **کیفیت صوت جلسات ایرانی** (تداخل، همهمه، نویز، فارسی محاوره + اصطلاح انگلیسی) — دقت دیاریزیشن افت جدی دارد | راهنمای ضبط یک‌صفحه‌ای برای تیم؛ قاعده‌ی عملی: یک موبایل وسط میز. کیفیت ورودی = کیفیت خروجی. مرحله‌ی ویرایش انسانی سبک قبل از نهایی‌شدن صورت‌جلسه. |
| **overlap گوینده‌ها** — این محدودیت فناوری است، نه باگ | انتظار را مدیریت کنید، در گزارش تست ثبت شود |
| **قطع/بی‌ثباتی اتصال به API** | زنجیره‌ی Gemini→Groq؛ اگر باز هم ناپایدار بود → Whisper خودمیزبان |
| **از دست رفتن داده** | بکاپ pg_dump شبانه — اولویت بالا |
| **خزش دامنه (scope creep)** | این سند مرز است. معیار خروج بخش ۹ دروازه است. |
| **تک‌نفره بودن نگهداری** | مالکیت ریپو + CI + مستندسازی نزد کارفرما از روز اول |

### Whisper خودمیزبان — جزئیات (برای وقتی لازم شد)
یک‌بار وزن مدل با VPN دانلود می‌شود (faster-whisper large-v3، حدود ۳GB)، از آن به بعد کاملاً آفلاین: نه سهمیه، نه وابستگی جغرافیایی.
**هزینه‌اش:** روی CPU کند است (جلسه‌ی ۶۰ دقیقه‌ای ≈ ۲.۵ ساعت پردازش — برای batch شبانه خوب است، نه فوری). روی GPU سریع. دیاریزیشن باز هم باید جدا با pyannote اضافه شود.
در نسخه‌ی فعلی نیست چون یک سرویس Docker و منابع جدید می‌خواهد.

## ۱۱. قواعد UI/UX (برای توسعه‌ی آینده — رعایت اجباری)

- **Hub-and-Spoke:** منوی اصلی ثابت (Reply Keyboard)، هر شاخه Inline Keyboard با «⬅️ بازگشت»
- **قاعده‌ی سه‌کلیک:** هیچ داده‌ای بیش از سه کلیک از منوی اصلی دور نیست. اگر شد، معماری منو غلط است.
- **Edit-in-place:** ناوبری با `editMessageText`، نه پیام جدید — چت شلوغ نمی‌شود
- **Pagination:** ۵–۸ آیتم per صفحه
- **تأیید مخرب دومرحله‌ای:** حذف و تغییر نقش
- **ورودی متنی حداقلی:** هرجا ممکن دکمه؛ تایپ فقط برای اسم و جست‌وجو
- **وضعیت پردازش شفاف:** سکوت = بی‌اعتمادی. صوت طولانی = پیام progress
- **جدول:** monospace کلاسیک روی موبایل فارسی می‌شکند — از Rich Messages یا خروجی فایل استفاده شود

### محدودیت‌های تلگرام که معماری را شکل داده‌اند
- سقف دانلود ۲۰MB / آپلود 50MB در API استاندارد
- نرخ ارسال: ~۱ پیام/ثانیه per چت، ۲۰/دقیقه در گروه، ~۳۰/ثانیه سراسری → نوتیف انبوه باید batch شود
- بات تاریخچه‌ی قبل از عضویتش در گروه را نمی‌بیند → **«ایمپورت گذشته» وجود ندارد؛ به کاربر صریح گفته شود**
- Privacy Mode در گروه پیش‌فرض روشن است → یا disable (با رضایت اعضا) یا الگوی «فوروارد به بات»

## ۱۲. فرمت گزارش تست (لطفاً همین قالب)

برای هر باگ:
```
عنوان:
مرحله‌ی بازتولید: ۱... ۲... ۳...
انتظار:
واقعیت:
لاگ (docker compose logs):
شدت: بلوکر / جدی / جزئی / UX
```

برای هر جلسه‌ی تست‌شده:
```
مدت صوت:
تعداد گوینده:
شرایط ضبط (محیط، فاصله میکروفن، تداخل):
provider که جواب داد: gemini / groq
کیفیت تفکیک گوینده: ۱–۵
کیفیت رونوشت: ۱–۵
کیفیت مصوبات استخراج‌شده: ۱–۵
مصوبه‌ای که جا افتاد:
مصوبه‌ای که اشتباه ساخته شد:
```

**کیفیت تفکیک گوینده‌ی فارسی باید روی صوت واقعی قضاوت شود، نه روی فرض.** این مهم‌ترین داده‌ای است که از این تست می‌خواهیم.

# پلی‌بوک پیگیری فروش (CRM) — و نگاشتش روی دیوان
**منبع:** راهنمای «Build an AI CRM that follows up for you» (@gobi_automates)
**چرا اینجاست:** این نسخه‌ی ساده و اسپردشیت‌محورِ زیرسیستم B دیوان است. ارزشش در ابزار نیست
(دیوان از آن جلوتر است)، در **انضباط عملیاتی** است. اینجا عصاره‌اش کشیده و روی معماری دیوان نگاشته شده.

---

## ۱. خلاصه‌ی سیستم — یک خط
`LEAD → ENRICH → QUALIFY → FOLLOW-UP → BOOK → TRACK → CLOSE`
اکثر معامله‌ها به‌خاطر بد بودن پیشنهاد از دست نمی‌روند؛ به‌خاطر **فراموش‌شدن پیگیری** از دست می‌روند.
کل هدف سیستم: هیچ لیدی فراموش نشود.

## ۲. چه چیزش واقعاً ارزشمند است (این‌ها را «یاد گرفتم»)
چهار قاعده‌ی طلایی که مستقیم به رفتار دیوان تزریق می‌شوند:

1. **«AI drafts, you send» — هوش پیش‌نویس می‌کند، انسان می‌فرستد.**
   → این **دقیقاً** همان اصل قفل‌شده‌ی دیوان است: «ایجنت پیشنهاد می‌دهد، انسان دکمه می‌زند».
   یک منبع بیرونی مستقل، همان تصمیم معماری ما را تأیید کرد.
2. **هر لید همیشه یک `Next Action` و یک `Next Date` دارد. بدون استثنا.**
   روال روزانه = صبح، شیت را بر اساس Next Date مرتب کن، از بالای لیست کار کن. ۵ دقیقه.
   → این ساده‌ترین و قوی‌ترین مکانیزم ضدفراموشی است و مستقیم روی مدل Task دیوان می‌نشیند.
3. **سه پیام، بعد توقف.** پیگیری حرفه‌ای است؛ پیگیری هفت‌باره آزار است.
   روز ۰ (باز کردن با چیزی مشخص) / روز ۳ (یادآوری کوتاه) / روز ۸ (ارزش + بستن مؤدبانه‌ی پرونده).
4. **امتیاز بده تا اولویت‌بندی کنی — نه اینکه همه را دنبال کنی.**
   ۵۰ امتیاز: FIT / NEED / URGENCY / BUDGET / AUTHORITY (هرکدام ۱۰).
   ۴۰–۵۰ امروز زنگ بزن · ۲۵–۳۹ سکانس کامل · ۱۵–۲۴ یک پیام · زیر ۱۵ رها کن.

قواعد اخلاقی/حقوقی هم دقیقاً هم‌راستای «مرز اخلاقی» و «نردبان اطمینان» RCE است:
فقط داده‌ی عمومی و قانونی · چیز نادرست از خودت درنیاور (یک اسم شرکت غلط = مرگ معامله) ·
opt-out آسان و فوری · CAN-SPAM/GDPR/TCPA حتی وقتی AI متن را نوشته، شامل تو می‌شود.

## ۳. نگاشت روی معماری دیوان — هر تکه کجا می‌نشیند

| تکه‌ی پلی‌بوک | در دیوان کجاست | وضعیت |
|---|---|---|
| شیت واحد لید (تک‌منبع حقیقت) | زیرسیستم B روی entity store (Twenty یا اسکیمای خودمان) | طراحی‌شده |
| ENRICH (شرکت/نقش/صنعت/…) | ایجنت غنی‌سازی → صف پیشنهاد → تأیید انسانی | لایه‌ی ایجنت |
| QUALIFY (امتیاز ۵۰) | نگاشت به بردار **Readiness (R)** در RCE — بخش ۴ | هسته/موتور امتیاز |
| FOLLOW-UP (۳ پیام) | «ایجنت پیگیری فروش» (contract پایین) + Task/Reminder | لایه‌ی ایجنت |
| BOOK (رزرو تماس) | ماژول زمان‌بندی (Cal.com/Cal.diy) + وبهوک به CRM | فاز اتصال |
| پایپ‌لاین ۶ مرحله‌ای | فیلد Stage روی لید + فید پروژه | هسته |
| TRACK (۶ عدد هفتگی) | ویجت‌های داشبورد نقش «مدیر فروش» | فاز اپ |
| Next Action + Next Date | مدل Task دیوان (مسئول + مهلت شمسی) | موجود ✅ |

**پایپ‌لاین:** `NEW → ENRICHED → QUALIFIED → FOLLOW-UP → BOOKED → CLOSED`
(یک فیلد Stage، شش مقدار — دقیقاً الگوی «برد قابل شخصی‌سازی» monday که در بریف گفتیم از آن وام می‌گیریم.)

## ۴. نگاشت امتیازدهی روی RCE — پل مهم
سیستم QUALIFY این راهنما، نسخه‌ی ساده‌شده‌ی بردارهای RCE است. این پل را برقرار می‌کنیم تا دو مدل یکی شوند:

| فاکتور راهنما (۱۰ امتیازی) | معادل در RCE |
|---|---|
| NEED (نیاز فعال دارد؟) | Readiness: active need |
| BUDGET (توان پرداخت؟) | Readiness: budget |
| AUTHORITY (خودش بله می‌گوید؟) | Readiness: decision authority |
| URGENCY (الان یا یه‌روزی؟) | Readiness: recent trigger + horizon < 6mo |
| FIT (مشتری دلخواه من؟) | تابعی از Resource vector (V) + demand-tag match |

نتیجه: امتیاز ۵۰تاییِ ساده برای کاربر مبتدی نمایش داده می‌شود، ولی **زیرِ کاپوت** همان بردار Readiness
با نردبان اطمینان (C) محاسبه می‌شود. مبتدی عدد ساده می‌بیند؛ حرفه‌ای بردار کامل. «هر آدمی با هر سطح سواد».

## ۵. ایجنت جدید برای Agent Registry — «ایجنت پیگیری فروش»
این راهنما دقیقاً قرارداد یکی از دو ایجنت اولِ نقشه‌ی راه را می‌دهد:
```
Agent: «پیگیری فروش»
contract.inputs:  رکورد لید (enriched) + امتیاز Readiness + لحن برند + لینک رزرو
contract.outputs: سکانس ۳ پیامی (متن + سابجکت + روز ارسال) — پیش‌نویس، نه ارسال‌شده
runtime:  n8n workflow یا Claude API
schedule: رویدادمحور (وقتی لید QUALIFIED شد) → پیش‌نویس پیام ۱
delivery: صف پیشنهاد → کاربر ✅ می‌کند → خودش می‌فرستد (AI drafts, you send)
budget:  سقف اجرا در ماه
قاعده‌ی سخت: سه پیام، بعد توقف. auto-send هرگز پیش‌فرض نیست.
```

## ۶. فیدبک صادقانه — کجا این ساده است، کجا دیوان باید سادگی‌اش را وام بگیرد
- **کجا دیوان جلوتر است:** تک‌کاربره نیست، multi-tenant است؛ داده‌ی انباشتی و ledger دارد؛
  امتیاز از تاریخچه مشتق می‌شود نه دستی؛ چندکاناله (تلگرام/بله) به‌جای فقط Gmail.
- **کجا باید از این وام بگیریم (مهم):** این راهنما یک درس بزرگ دارد — **START CHEAP و روی یک لید واقعی امروز تست کن.**
  دیوان با جاه‌طلبی‌اش در خطر over-engineering است. «کوچک‌ترین چیز قابل‌عرضه در ۴ هفته» که در بریف خواستیم،
  دقیقاً باید همین حلقه‌ی ساده باشد: لید → امتیاز → ۳ پیام پیش‌نویس → تیک. نه یک ثانیه بیشتر.
- **درسی که مستقیم برمی‌داریم:** قاعده‌ی «Next Action + Next Date روی هر رکورد، همیشه» را به‌عنوان
  یک **قاعده‌ی اجباری مدل داده** در دیوان قفل می‌کنیم — هر Task/Lead بدون Next Date نامعتبر است.

## جمع‌بندی
این پلی‌بوک ابزار تازه‌ای به دیوان اضافه نمی‌کند؛ **انضباط** اضافه می‌کند و «ایجنت پیگیری فروش» و
مدل امتیازدهیِ ساده‌ی رو-به-کاربر را دقیق می‌کند. مهم‌ترین چیزی که تأیید کرد: اصلِ «AI پیش‌نویس، انسان ارسال»
درست است و بازار هم همان را می‌گوید. این به‌عنوان spec رفتاریِ زیرسیستم B در کار قفل شد.
